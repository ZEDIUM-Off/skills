# Plan Writer Reference

## Invariants

- Assume grilling already happened. Do not restart grilling by default.
- Ask the user only for human/product decisions that cannot be resolved from code, docs, or focused subagents.
- All implementation subagents are `fresh`; do not use forked context.
- Large plans are allowed. Split only assignable units that are not bounded/fresh-executable.
- Drafts and gate iterations stay in chat. Persist only the final approved plan.
- The final plan is a blueprint, not a scratchpad: include only verified facts, explicit decisions, accepted constraints, actionable orchestration, exact task scopes, exact references, and review flags.
- Do not include generic provenance. Attach references exactly where the orchestrator or subagent needs them.

## Final artifact

Final plan path:

```text
.agents/plans/<slug>.md
```

Slug rules:

- kebab-case;
- derived from the plan title;
- no date prefix;
- create `.agents/plans` if missing;
- never overwrite silently.

If the file exists, read it and ask whether to update in place, create a variant, or abort.

## Gates

### Gate 1 — Intake frozen

Capture goal, non-goals, known decisions, constraints, initial review flags, and likely package/domain boundaries.

Completion criterion: the plan objective and boundaries can be stated without asking another broad discovery question.

### Gate 2 — Technical resolution complete

Resolve technical/codebase uncertainty before the final plan:

- inspect relevant files and symbols;
- load relevant skills;
- fetch/read docs if required;
- launch focused subagents/chains if useful;
- identify exact files to create/modify/delete;
- reduce remaining flags to human/product decisions, real contradictions, or accepted risks.

Completion criterion: no final task contains unknown file scope or unresolved technical discovery that the planning agent could have resolved.

### Gate 3 — Task graph stable

Define phases, waves, tasks, and optional subtasks.

Rules:

- phases may be broad milestones;
- tasks may be containers or assignable units;
- subtasks may be used for smaller assignable units;
- only units marked `Assignable: yes` are launched;
- every assignable unit is bounded and fresh-executable;
- same-file write/write units are sequenced unless an explicit safe partition is established; prefer sequencing;
- expose final parallelization constraints, not exploratory matrices.

Completion criterion: every assignable unit has exact dependencies, exact file scope, and a clear validation responsibility.

### Gate 4 — Draft reviewed

Run or simulate focused review. Prefer parallel subagents when useful:

- feasibility / missing file references;
- sequencing / parallelization / dependency graph;
- scope isolation / prompt quality.

Review checklist:

1. Each assignable unit is fresh-executable.
2. Files are exact.
3. Dependencies are coherent.
4. Parallel units do not write the same files.
5. Prompts prevent scope leakage.
6. References are sufficient and attached at point of use.
7. Review flags are visible and actionable.
8. Snippets/artifacts are tagged `[CANONICAL]` or `[ILLUSTRATIVE]`.
9. Acceptance criteria are testable.
10. Output contracts and handoffs are usable.

Completion criterion: required review changes are applied, and remaining concerns are explicit review flags.

### Gate 5 — Blueprint finalized

1. Copy `templates/implementation-plan.md` to `.agents/plans/<slug>.md` or update the approved existing plan.
2. Fill variable sections.
3. Keep invariant template text unless there is a deliberate reason to change it.
4. Use stable anchors for line-reference targets.
5. Run:

```bash
node /Users/matissechenavas/.agents/skills/plan-writer/scripts/finalize-plan-lines.mjs .agents/plans/<slug>.md
```

6. Read the generated line-reference table and verify coherence.
7. Report the final path and remaining review flags.

Completion criterion: the final Markdown exists, contains generated line references, and can be executed by a fresh orchestrator without this skill.

## Required final plan sections

- How to use this plan.
- Legend.
- Goal / non-goals.
- Review flags table.
- Global acceptance criteria.
- Legacy/workaround policy.
- Planned breaking changes and propagation map when relevant.
- Subagent orchestration waves listing only assignable units.
- Parallelization constraints summary when relevant.
- Canonical line references generated by script.
- Phases/tasks/subtasks with stable anchors.
- Subagent prompts for each assignable unit.
- Pre-finalization review summary.

## Assignable unit contract

Each `Assignable: yes` unit must include:

- stable anchor and ID;
- wave, fresh context, dependencies, allowed parallelism, prohibited parallelism;
- goal, non-goals, forbidden work;
- exact files created/modified/deleted;
- context package with plan references, dependency output references, neighboring out-of-scope references when useful, files/symbols to read, skills, and docs/URLs;
- implementation outline;
- major snippets only, tagged `[CANONICAL]` or `[ILLUSTRATIVE]`;
- explanatory artifacts when useful:
  - UI/UX layout: ASCII wireframe;
  - API/workflow sequence: Mermaid sequence diagram;
  - data model/module relationships: Mermaid ER/class diagram;
  - task dependency graph: Mermaid flowchart;
  - state machine: Mermaid state diagram;
  - file/module ownership: table;
  - cross-package contract propagation: Mermaid flowchart or table;
- validation responsibility;
- output contract;
- acceptance criteria;
- handoff to dependent units;
- subagent prompt.

## Validation responsibility

- `non-validating`: may intentionally leave broader breakage for later units. Must not run global compile/lint/test gates unless explicitly allowed.
- `locally-validating`: validates only owned scope.
- `integration-validating`: owns broader compile/lint/test/integration gates.

For `non-validating` units, explicitly list commands not to run. This prevents global validation and workaround patches.

## Legacy/workaround policy

Plans must prevent artificial compatibility fixes unless explicitly required:

- no temporary aliases unless listed as allowed;
- no compatibility shims unless they are the goal of a task;
- no type weakening to satisfy intermediate compilation;
- no preserving legacy names when the goal is removal/rename;
- do not expand scope to fix breakages assigned to later units;
- if blocked, report the breakage and reference the downstream unit responsible.

For renames/removals/contract changes, add a planned breaking changes propagation map.

## Revision mode

When revising an existing plan:

1. Read `.agents/plans/<slug>.md`.
2. Extract existing goals, task graph, flags, file scopes, prompts, validation responsibilities, output contracts, and handoffs.
3. Compare with new decisions/request.
4. Produce proposed changes in chat only.
5. Iterate gates as needed.
6. Write only after explicit approval.

Revision chat output includes target file, change summary table, task graph impact, planned file-scope changes, and whether renewed grilling is recommended.
